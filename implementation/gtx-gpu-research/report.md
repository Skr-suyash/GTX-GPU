# GTX-GPU: results report

**Problem.** Atomic multi-edge transactions (insert/delete edges, point reads, adjacency scans) on a GPU-resident dynamic
graph, with **concurrent snapshot readers**, fixed vertex set, SI and serializable configurations.
**Machine.** RTX 4060 Laptop GPU (Ada sm_89, 24 SMs, 8 GB, WDDM), CUDA 12.8, Windows 11. All numbers are local,
matched measurements (same generated stream and seed for every system; median of 5 repetitions after a warm-up;
speedups = ratio of median *committed-transaction* throughput with 95% bootstrap CIs; `results/speedups.csv`).

> **Two campaigns.**
> - **Part A** (2026-11, `results/v2/`) holds the current numbers. They were measured with the final binaries in one
>   session (`scripts/campaign_v2.py`).
> - **Part B** (2026-09, `results/`) is kept unchanged for the record.
>
> Every kernel ran 1.4–2.7× faster in 2026-11 than in 2026-09. The September source rebuilt with the November
> compiler times identically, so the shift is not caused by the code or the compiler. The system-side cause (driver
> 621.01, power/clock state) was **not isolated** (`protocol/reproduction_protocol.md`).
> Absolute numbers from the two parts must not be mixed. Ratios are reproduced within each part.

# Part A — 2026-11 campaign (current)

## A1. What was added since 2026-09

- **Correctness proof** (`design/proof.md`): a paper proof of snapshot isolation (Theorems 1–4) and serializability
  (Theorem 5) against the PTX memory model, with every lemma mapped to a code site and a test.
  - The proof found two latent ordering gaps that the history checker cannot observe on this GPU:
    - **D11:** commit registration relied on `__ballot_sync`/`__shfl_sync`, which carry no memory ordering;
    - **D12:** in cooperative scans, other lanes could on paper see a stale generation list.
  - Both are fixed, and the fixes cost ≤ 1% (`results/defect_log.md`).
- **Correctness gate extended to sections A–H** (`results/v2/correctness_suite.txt`): **109 cases, 0 unexpected.**
  - Sections A–E: 67 base cases.
  - Section F: Method 4 histories, including races between merges and cooperative scans or SER validation, and
    forced-truncation merges.
  - Section G: five M4 mutations, four of them observable and all four rejected. The fifth is a SIMT-lockstep hazard
    that is not observable on this GPU and is covered by the proof only.
  - Section H: arena exhaustion with reuse.
- **Checked campaign runs:** 50 history-checked runs over every system, including the `gtx-gs1` layout, plus the new
  bulk-loader, batch-mode and SNAP-file paths. All PASS, no flags (`results/v2/summary.csv`, `check-*` rows).
- **Method 4** (generation merging + block reuse) was implemented, gated, and **falsified** against criteria fixed
  before measurement (A5).
- **Memory was measured before redesign.** The 2.5–20× overhead is mostly *layout*, not garbage (A5).
- **Real graphs:** four SNAP graphs as sliding-window streams (A3).
- **Batch-size sweep** against GPMA+ (A4).
- **Uncontended gap to 2PL:** bounded; the write path cannot close it (A6).
- **faimGraph:** a driver on identical streams was written but not built. Building the cloned third-party code was
  not permitted in this session (`baselines/faimgraph/PORT_NOTES.md`). Hornet, SlabGraph and LPMA are Linux-only or
  unavailable, so they remain paper-only.

**Reading the real graphs.**
- **wiki-Talk**, with a 100K-degree hub, behaves like the synthetic hub cells: GTX-GPU wins by one to three orders of
  magnitude over 2PL and TL2.
- **Graphs without extreme hubs** (roadNet, cit-Patents) behave like the uniform cells: GTX-GPU is 0.66–0.84× of
  2PL on update and SER streams. With 90% readers on cit-Patents it is 1.12×. It still beats word-STM with a degree
  word, except on K=1 churn.
- **soc-pokec** sits between the two: it is about level with 2PL, and wins as readers grow (1.19× 2PL, 6.8× TL2).
- **Against GPMA+**, GTX-GPU is faster on every real stream, and GPMA+ verifies correctly on all of them (disjoint
  insert and delete keys).
- **M4 and the 2× layout** are within ±10% of `gtx` on every SNAP stream (`results/v2/summary.md`).

## A4. Batch-size sweep against GPMA+ (uniform churn, 4M ops, total GPU time)

GTX-GPU is run as one kernel launch per batch, with the frontier published between launches. That is GPMA+'s unit
of atomicity, which gives GTX-GPU no cross-batch overlap.

| batch | GTX-GPU ms | GPMA+ upstream / port ms | GTX-GPU speedup vs faster GPMA+ |
|---:|---:|---:|---:|
| 2^10 | 224.9 | 3,198.7 / 3,319.2 | 14.2× |
| 2^12 | 59.5 | 978.9 / 1,050.1 | 16.5× |
| 2^14 | 27.9 | 298.0 / 292.5 | 10.5× |
| 2^16 | 20.9 | 124.4 / 123.9 | 5.9× |
| 2^18 | 19.0 | 99.0 / 103.3 | 5.2× |
| 2^20 | 18.5 | 80.5 / 77.1 | 4.2× |
| 2^22 | 18.4 | 33.4 / 36.5 | 1.8× |

- GTX-GPU's time is flat from 2^16 upwards. Below that, kernel launches dominate.
- GPMA+ amortises its sort and rebalance only at very large batches.
- On this synthetic churn stream, GPMA+'s final state is **wrong at every batch size**: 86 wrong edges at 2^10,
  rising to 360,800 at 2^22. A batch can contain an insert and a delete of the same edge, and GPMA+ does not
  preserve their order.

## A5. Memory: measured breakdown, Method 4, and the layout choice

**Where the bytes are** (`--membreak`, `results/v2/layout_sweep.csv`):
- **Unwritten capacity** in each vertex's newest generation, from the 8× growth ladder and `minCap = 8`, is 43–61% of
  all bytes.
- **Chain heads** scale with capacity.
- **Reclaimable garbage** (voided + aborted + dead + DEL) is 0% for uniform inserts, 4% for Zipf churn, 9% for
  identical-edge-1024 and 14% for identical-edge-64.

**Layout alone.** With 2× growth (`gtx-gs1`):
- bytes drop 20% (uniform), 33% (R-MAT readers), 36% (identical-edge-1024) and 55% (identical-edge-64), at ≤ 1% time
  on uniform and hot cells;
- it costs 17–30% on skewed live-insert workloads (hub, R-MAT churn, Zipf churn), because writers walk every older
  generation (7 → 18).

**Method 4 is falsified on its pre-registered criteria P1 and P2** (`design/design.md` §7 M4,
`results/v2/m4_diagnosis.md`).

| | identical-edge-64 | identical-edge-1024 | other 24 main/SER cells |
|---|---|---|---|
| bytes: `gtx` → `gtx-m4` (`gtx-gs1`) | 1486 → 721 MB (671) | 749 → 636 MB (480) | ≈ unchanged |
| time, `gtx-m4` vs `gtx` | 0.66× | **0.33×** | 0.87–1.04× |

The diagnosis:
- Hold-sizing alone deepens hot vertices to 170 generations.
- Merging bounds that depth, but each merge re-copies most live versions: 84% of linked versions were kept on the
  1024 cell.
- **The plain 2× layout dominates every merge-based variant** on time and memory. The permitted exploratory revision
  was therefore not run.

M4's announce/EBR/forwarding machinery is correct (gate F–H, proof §8) and stays in the code, off by default. The
review found and fixed one real hole in it, the truncated-merge DEL drop. The checker rejects its mutation.

P3 (correctness) **fails as registered**: the gate passes everywhere, but only 3 of the 4 registered M4 mutations are
rejected. The per-lane generation-list mutation (`dbg 128`) is not observable on this GPU (SIMT lockstep) and is
covered by the proof only. The later truncated-merge mutation is also rejected (gate section G: 4 of 5 observable).

**Recommendation:** choose growth per workload.
- `growShift = 1` for uniform and contended workloads: −20% to −55% bytes, no time cost.
- `growShift = 3` for skewed live inserts.
- Even at the best layout, GTX-GPU uses 3–9× the bytes of the pre-sized hash-table baselines (e.g. 402 vs 80 MB on
  uniform inserts; 315 vs 97 MB on R-MAT readers). Live versions alone are 154 MB on uniform inserts, against 80 MB
  for 2PL in total.

## A8. Method 5: quiescent compaction (bounded memory over long streams)

Between kernel launches, M5 rebuilds the version store from the graph visible at the frontier (proof §9, gate
section I, criteria Q1–Q4 in `design/design.md` §7 M5). Runs use 64 rounds of 2^18 transactions, K=4, 50/50
insert/FIFO-delete, a 20M-slot arena, and 1 run per cell (`results/m5/longrun.log`; `python -P scripts/analyze_m5.py`). The
policy (trigger, `growShift 1`, slack 100) was **chosen after registration** from `results/m5/sweep.log`.

| workload | `gtx` clean rounds | M5 rounds | M5 peak MiB | last/mid | M5 vs `gtx` 60M arena | pause p50/max ms |
|---|---:|---:|---:|---:|---:|---|
| uniform churn | 2 | 64 | 748 | 0.999 | 0.79× | 10.2 / 13.6 |
| Zipf churn | 1 | 64 | 714 | 1.001 | 0.70× | 10.0 / 13.2 |
| identical-edge-1024 | 1 | **28 (OOM)** | 802 | – | 0.81× | 9.4 / 16.4 |
| same, 40M arena | – | 64 | 1352 | 1.107 | – | 12.6 / 20.7 |
| R-MAT 90% readers, registered default | 13 | 64 | 723 | 0.994 | **1.36×** | 11.1 / 13.3 |

- **Q1 is met on uniform and Zipf.** Memory stays flat over 64 rounds (67M effective writes against a 20M-slot arena). The uncompacted store runs out
  within 1–7 rounds.
- **Q1 fails on identical-edge-1024.** That stream's *live* graph grows from 4.0M to 10.3M edges after round 15. The live count is identical under every compaction schedule,
  so this is the stream, not a leak. M5 memory follows
  the live graph (about 130 B per live edge), but it cannot be constant.
- **Q2 passes, but almost vacuously.** `gtx` survives only 1–2 rounds, so the window is nearly empty. Against a 60M arena
  over its 7, 22 and 4 clean rounds, the cost is 0.70–0.81×. The registered default policy (compact nearly every round) costs 0.31–0.49×.
- **Read-heavy streams gain.** On R-MAT with 90% readers, compaction keeps rounds at 5.7 ms instead of letting them
  grow to 12.2 ms. This holds for the registered default. The tuned policy never triggers on R-MAT
  (last/mid 1.108).
- **Q3 fails as registered**, the same way M4's P3 did.
  - The full gate A–I runs 219 cases with 0 unexpected results, 110 of them in section I across three kernel
    variants (`results/m5/gate_full.txt`).
  - The checker rejects two of the three registered mutations: drop a live edge, and keep invalidated versions.
  - Compacting at F − 1 is not observable at a launch boundary (proof §9), so it is informational.
  - A stale-frontier F/2 substitute, added after the fact, is rejected.
- **Q4.** Pauses are about 2.5 ms per million live edges and stop the world.
- **Limits.**
  - M5 needs launch boundaries.
  - A launch whose growth exceeds the 1.5× margin can still run out inside the kernel.
  - It requires `m4 = 0`.

# Part B — 2026-09 campaign (historical, unchanged)

## 1. Summary

GTX-GPU adapts GTX's versioned edge deltas, delta chains, descriptors and group commit to the GPU. The GPU-specific
changes: destination-precise conflict detection with validate-then-CAS on one observed head, block generations with
lazy chain sealing, a fused generation+fill reservation word with warp-cooperative reservation, wait-free epoch
registration, and Silo-ordered serializable validation.

* **Correct under a history checker, not just a final-state diff.** Every read, no-op write and scan is checked
  against its snapshot. The checker also verifies write-write exclusion and serialization-graph acyclicity. It passes
  48 adversarial histories, a write-skew probe (SI must show the anomaly, SER must not), and all baselines. It rejects
  3 deliberately broken protocols, two of which pass the earlier prototype's log-vs-final check. It found 5 real
  protocol defects during development; all are fixed (`results/defect_log.md`).
* **Large speedups where synchronization is actually hard** (contention, power-law graphs, concurrent readers, large
  transactions, serializable read-write transactions). The comparison is against conventional GPU synchronization
  (2PL vertex locks, TL2 word-STM) on the *same* storage, and against GPMA+ on the same streams.
* **Honest losses:** slower than 2PL on uniform, low-contention, small transactions (1.3–2.1×); slower than a
  degree-free STM on write-only contention (1.0–1.6×); always slower than non-transactional CAS (no atomicity);
  2.5–20× more memory (no reclamation yet).

## 4. Correctness evidence
* `bin/test_gtx.exe full`: 6 adversarial workloads × {SI, SER} × {cooperative reservation on/off} ×
  {destination/chain conflicts} = 48 histories, all **PASS** C1–C5. Write-skew probe: SI shows 16,000 dependency-graph
  back edges (the anomaly is allowed and the detector is live); SER shows 0. Resource exhaustion: the committed prefix
  is consistent.
* Mutation tests (`results/mutation_final_state.txt`):

  | mutation | prototype-style "logged set == final set" | new checker |
  |---|---|---|
  | no write-write check | passes (0/0) | 4,386 C3 + 10,984 same-epoch writers, 6,557 cycles |
  | ignore snapshot | passes (0/0) | 9,658 wrong reads + 5,382 wrong scans |
  | dirty reads | detected | 11,411 + 6,972 + 271,175 cycles |
* All baselines (2PL, TL2 STM ± degree) pass the same checker in serializable mode (`run_matrix.py check`), including
  their cooperative read-only variants.
* Defects found by the checker and fixed before benchmarking: registration livelock (D5), epoch-after-validation
  read-only anomaly (D6), read-only commit exposing voided slots (D7), a missing happens-before edge on generation
  growth (D8), and an unsafe watchdog (D9). See `results/defect_log.md` and `audit/prototype_audit.md`.

## 6. Fairness notes
* Baseline hash tables are pre-sized from the workload and never grow; GTX-GPU grows at run time (favors baselines).
* Scans: GTX-GPU scans cooperatively by default. Baselines were run both per-lane and with cooperative read-only scans
  (`-roCoop` labels); every headline comparison uses the **better** of the two for each baseline. GTX with per-lane
  scans is also reported (`-lanescan`).
* 2PL uses sorted blocking vertex locks for update transactions and bounded try-locks for cooperative read-only
  transactions (a blocking lock inside a warp collective can deadlock).
* GPMA+ provides batch atomicity only, no multi-edge transactions or concurrent readers, and loses intra-batch
  operation order: its final state differs from sequential semantics on hub and churn streams (duplicates within a
  batch; INS/DEL of one edge in one batch). Its Windows port and pristine upstream (CDP1) run at the same speed on
  these streams (≤2% apart), so the port does not distort these comparisons.
* Literature numbers (`benchmarks/benchmark_inventory.*`) are reference points only (TITAN V / P100 / 2080 Ti, other
  datasets). Examples: SlabGraph 501–641 MEdge/s insert without transactions; LPMA 6–20× over GPMA+; GTX (CPU) up to 11×
  over LiveGraph/Teseo/Sortledton. No cross-hardware claims are made.

## 7. Limitations and next steps
1. Reclamation / consolidation by generation (M4) to remove the 2.5–20× memory overhead and speed up scans.
2. Close the uncontended gap to 2PL: fewer bytes per version (split hot/cold delta fields) and cheaper per-attempt
   bookkeeping.
3. Real SNAP graphs and batch-size sweeps (2^10–2^22) against GPMA+; build LPMA / Hornet / faimGraph / SlabGraph on this
   machine for matched storage-level comparisons (currently paper-only).
4. Descriptor reuse (generation-tagged ids), vertex insertion/deletion, and durability are out of scope of this prototype.
